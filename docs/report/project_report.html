1. Summary

The project builds a scheduler that decides, for each LLM request on a single CPU machine, how the model should be executed. TinyLlama-1.1B runs layer by layer through a hand-written decode loop. Its 22 decoder layers are split into stages, and each stage gets its own intra-op thread budget. Three execution strategies exist (static, balanced, latency_optimized). All of them give token-identical output to Hugging Face model.generate(), so the choice only affects speed.

The work went through seven phases. The early versions (v1/v2) produced results that turned out to be noise, because the strategies were computationally identical and were measured one after another. v3 fixed both problems. Strategies now differ in thread budgets, and measurements are paired and randomized under controlled background CPU load. A contextual-bandit DQN was then trained on the v3 data. After that the project moved to its main idea, re-deciding the strategy every 10 tokens during generation, plus an online bandit that keeps learning from measured token latency.

Main results
  • Which strategy is fastest depends on load. Idle machine: 10 threads (static) wins. Around 8 busy workers: 6 threads. At 10-14 busy workers: 3+3 threads (balanced). At 12 workers static oversubscribes the CPU and is about 18x slower per token than balanced (2.14 s vs 0.116 s per token).
  • Re-scheduling during generation pays off when load rises sharply. In the v5 ramp scenario (idle, then 8, then 12 workers) the DQN re-deciding every 10 tokens took 54.9 s, against 389.5 s when it decided once per request. That is 85.7% faster (paired 95% CI -430 to -266 s, n=6). In relief it was 10.7% faster than deciding once (CI -5.3 to -2.3 s).
  • In v4 the online bandit beat the per-request DQN by 7.8% (spike) and 7.0% (relief), and corrected a stale offline model.
  • In v5, with harsher load levels, the online bandit was the weakest adaptive policy. It was 57% slower than fixed balanced in spike and 34% slower than the re-deciding DQN in ramp. Section 11 gives the evidence and the likely causes.
  • Output stayed token-identical across all conditions in 100% of contexts in v4 and v5. Decision overhead is 2-5 ms per 200-token request (0.21 s in v3).

2. Problem and goal

LLM inference on a shared machine competes with other processes for CPU. A single fixed execution configuration is only best for one load level. Too many threads under contention cause oversubscription and context switching. Too few threads on an idle machine waste cores. The goal is a scheduler that observes the request and the system state and picks the execution plan (layer partition plus thread budget) that minimizes latency, without changing the model's output.

Most schedulers decide once per request, before the first token. A long response can take tens of seconds, and load can change during that time, so the per-request decision goes stale. The innovation chosen for this project is intra-generation re-scheduling. Because every strategy here shares the same weights and the same KV cache, the engine can switch strategy between two tokens at no cost and with identical output.

4. System design

4.1 Layer-sliced inference engine

src/llm/inference.py runs TinyLlama without model.generate(). It embeds the prompt, then runs the decoder layers stage by stage with a shared KV cache, applies the final norm and LM head, and samples greedily. Before each stage it sets torch.set_num_threads() to that stage's budget. Between stages it records an activation handoff (an in-process clone(), timed and sized). The model is loaded lazily and once.

generate_partitioned_response(prompt, strategy, scheduler=..., decision_interval=N) accepts a scheduler object. Every N tokens it calls scheduler.decide() and switches strategy when asked. All runs in v4/v5 generate exactly 200 tokens (ignore_eos), so latencies are comparable across conditions.

Strategies are defined in configs/config.yaml and loaded by src/config.py. src/llm/partition.py turns them into stage definitions, and src/graph/execution_graph.py builds a networkx execution graph (Input, Tokenizer, LLM, Decoder, Output) annotated with the chosen partition, layer ranges and stage threads.

4.3 Telemetry and load generation

  • ExternalLoadMonitor measures system CPU minus this process's own CPU, so the scheduler reacts to other processes and not to its own inference threads.
  • BackgroundLoadSampler (v4) runs that measurement in a daemon thread with smoothing. Reading it never blocks generation. In v3, blocking telemetry cost 0.21 s per request.
  • BackgroundCPULoad starts N busy-loop worker processes for a whole request. DynamicCPULoad changes N over time. TokenScheduledLoad (v4) changes N after a given number of generated tokens, so every policy meets the load change at exactly the same point of the response.

4.4 Schedulers and policies

ConditionWhat it does
static, balanced, latency_optimizedFixed strategy for the whole request (baselines)
rule_adaptiveThreshold rule on external CPU (60% in v5): below it use static, above it balanced. Re-decided every 10 tokens with hysteresis
rl_onceOffline DQN, decides once before the first token
rl_adaptiveSame DQN, re-decides every 10 tokens with hysteresis
bandit_adaptiveOnline contextual bandit (OnlineBanditPolicy) that learns from measured seconds per token while it serves

Hysteresis (patience=2) means a policy only switches after it proposes the same new strategy in two decisions in a row. This stops flapping on noisy readings, but it also means a switch takes at least 20 tokens after the load changes.

4.5 The online bandit

Each 10-token segment is one bandit round. The context is the external-CPU bin, the arm is the strategy, and the cost is the measured seconds per token of the segment just generated (the first segment, which contains prefill, is skipped). Features:

  • Warm start from the offline DQN's Q-values with 2 pseudo-observations per arm.
  • Discounted estimates (discount 0.98 per round in a bin) so stale data fades when the machine drifts.
  • UCB-style exploration bonus (0.08) so arms not tried recently are re-checked, at the price of one segment.
  • Stall rejection (v4.1): a segment more than 2x slower than the best estimate in its bin is ignored, unless 5 arrive in a row, in which case the bin is reset and relearned.
  • Bin hysteresis: the bin only changes within a request when the reading moves more than bin_margin points past an edge (v5: edges 51% and 63%, margin 4).
  • One instance keeps learning across all requests. Its state is saved to adaptive_bandit_state_*.json so interrupted runs can resume.

4.6 Offline RL component

The DQN (src/rl/dqn_agent.py) is an MLP with two hidden layers of 64 units, input [prompt_length, input_tokens, cpu%, ram%] and one Q-value per strategy. Since requests are independent, it is trained as a contextual bandit with gamma=0. The logged data contains the outcome of every strategy in every context, so all three rewards are learned per context (full feedback). The reward is negative seconds per generated token. CPU and RAM penalties exist in src/rl/reward.py but are off by default, because post-run snapshots were too noisy. Features are built by one shared function (src/rl/features.py) for training and serving.

5. Phase 1 (v1/v2): first pipeline and why its results were noise

The main branch has the first full pipeline: Alpaca prompts, TinyLlama inference, CPU/RAM telemetry, a DQN scheduler and evaluation scripts. The v2 work then added the layer-sliced engine. Results from that stage:

The rankings flip between runs. Review of the code showed why: in v1/v2 the three strategies did the same computation with the same threads, only grouped differently. All runs of one strategy were also done before the next one started, so system drift (other apps, thermal state, memory pressure) was confounded with the strategy. The differences were noise. These files are kept as *_v2.csv for reference and are not used for conclusions.

6. Phase 2 (v3): real strategies and a corrected methodology

Commit 5291ab2 changed the strategies so they execute differently (per-stage thread budgets, still fp32 and token-identical). It also changed the measurement protocol. Strategies are now run back to back in random order within the same context (prompt, repeat, load level), after warm-up, under a controlled number of background busy workers. The state is measured before the decision, real generated token counts are used, and results come with bootstrap 95% CIs and paired differences.

7. Phase 3: contextual-bandit DQN

The DQN was trained for 200 episodes on the v3 data with full feedback, with prompts split into train and held-out validation sets. On the 15 held-out contexts it had zero regret in 6 of them and a mean regret of 0.049 s per token against the oracle (best strategy in hindsight). It learned the main pattern in the data: mostly static at 0-2 workers and balanced at 4-8 workers. The model is saved as data/processed/dqn_model_v3.pth and is the offline policy used in all later runs.

8. Phase 4: intra-generation re-scheduling (v3 adaptive)

Commit 3f42bdb added re-scheduling during generation and evaluate_adaptive.py. Four scenarios: steady_idle, steady_heavy, spike (load arrives mid-request) and relief (load leaves mid-request). Six conditions were compared on 60-token requests with time-triggered load, 3 prompts per scenario.

Result: no benefit. rl_adaptive was not significantly different from rl_once in any scenario, and was 35% slower than fixed latency_optimized in spike. Three causes were found: 60-token requests were too short for a mid-request change to matter, the time-triggered load did not hit every policy at the same token, and blocking telemetry cost 0.21 s per request. RAM pressure had also changed since the v3 data was collected, so the offline DQN was already stale. These findings drove the v4 design.

9. Phase 5 (v4): online bandit

v4 setup: 10 prompts x 4 scenarios = 40 contexts, 7 conditions, 200 tokens per request, decision every 10 tokens, load triggered by token count, non-blocking telemetry. Two contexts with memory-paging stalls (a run more than 2x the scenario median) were excluded. Raw data is kept.

  • The bandit was significantly faster than the per-request DQN when load changed mid-request: -7.8% in spike, -7.0% in relief. It was also significantly faster than rl_adaptive in spike and steady_heavy, and than the threshold rule in three scenarios.
  • It corrected a stale offline model. The v3 data said balanced wins under load. At v4 time the 6-thread latency_optimized won everywhere. The DQN kept choosing balanced; the bandit moved to latency_optimized.
  • Regret against the best fixed strategy in hindsight: 0.3-1.2 s per request for the bandit, 0.9-2.1 s for the DQN. Bandit regret fell from 0.94 s to 0.66 s between the first and second half of the run, so it was learning.
  • Limitation: one fixed strategy happened to be near-optimal everywhere, so the bandit only tied it in spike and steady_idle and was 4-6% slower in relief and steady_heavy. That is the cost of exploration (about 3 switches per request).
  • Decision overhead fell from 0.21 s (v3) to 0.002 s per request.

v4 diagnostics also showed two bandit problems, both fixed in commit 3c2fc89. Paging stalls had poisoned its estimates, which led to stall rejection and bin reset. Readings near a bin edge caused bin flapping, 53 of 114 switches, which led to bin hysteresis. Forgetting was also slowed (discount 0.98) and the exploration bonus reduced (0.08).

11. Phase 7 (v5): multi-level load and the ramp scenario

v5 setup: 8 prompts (prompt IDs 21-28, unseen in training) x 5 scenarios = 40 contexts, 7 conditions, 280 requests of 200 tokens each. Heavy phases use 10 workers, load changes at token 60. The new ramp scenario goes idle, then 8 workers from token 60, then 12 from token 140, so no single fixed strategy is best for the whole response. The run was paused on 11 October with 5 contexts done. One paging-corrupted context was removed (a backup is in data/processed/v5_backup). A Windows scheduled task then resumed it at midnight with --resume --keep-awake, and it finished at 04:56 on 12 October. Four contexts with paging stalls (IDs 14, 19, 36, 39) are excluded, leaving 36 (6-8 per scenario). Token output was identical across all conditions in 100% of contexts. Mean decision overhead: 0.005 s per request.

This is the clearest result of the project so far. In ramp the DQN sees an idle machine at the start and picks static. Deciding once, it keeps 10 threads when 12 workers arrive at token 140 and hits the oversubscription cliff (389.5 s). Re-deciding every 10 tokens it moves away from static and finishes in 54.9 s, 7.7% faster than the best fixed strategy (balanced, paired CI -7.1 to -2.7 s). 11.3 The spike scenario: switching too late

In spike all three adaptive policies (rule, DQN, bandit) were about 58% slower than fixed balanced (rule: +21.8 s, CI 11.8 to 32.1). The per-token timeline (Figure 4) shows why. The policies run static while the machine is idle. When 10 workers arrive at token 60, static slows to about 2.5 s per token, and the policies need 10-15 more tokens to switch: one decision interval (10 tokens) plus hysteresis (2 matching decisions), plus telemetry smoothing. Those few tokens at 2.5 s cost more than everything else. Fixed balanced pays about 10% on the idle part but never hits the cliff.

The v4 result did not carry over. The bandit's logged history explains part of it. In the high-load bin (above 63% external CPU) it accepted 104 segments of balanced with a median of 0.132 s per token, and 267 segments of latency_optimized with a median of 0.234 s per token, so it chose the slower arm about 2.5 times as often. In spike it never chose balanced at all (101 decisions on latency_optimized, 59 on static). Likely contributors, not yet confirmed:

  • The DQN warm start favours latency_optimized/static in bins it was not trained on (the v3 data stopped at 8 workers, about 75% CPU).
  • Per-segment cost includes the time spent before a switch takes effect, so the arm active right after a load change gets blamed for the previous arm's slow tokens, or the reverse.
  • The stall rule (reject segments more than 2x slower than the best estimate) can throw away genuine evidence when a load level really does make one arm 2x slower.
  • The bandit keeps exploring static in the low bin (324 segments) and pays for it when load arrives within that request.

Learning still happened. Mean regret against the best fixed strategy fell from 12.88 s in the first half of the run to 7.85 s in the second half. It stayed above rl_adaptive (6.30 s to 4.22 s) in both halves.

Honest reading of v5: re-scheduling during generation is clearly worth it when load rises past the oversubscription cliff (ramp: -86% against deciding once). The simple threshold rule and the re-deciding DQN got most of that gain. The online bandit, which was the best policy in v4, was the worst adaptive policy in v5, and needs to be fixed before it can be claimed as a contribution.

12. Methodology and statistics

  • Paired, randomized measurements: all conditions run back to back on the same prompt under the same load scenario, in shuffled order, after a warm-up generation. This removes the run-order confound of v1/v2.
  • Pre-decision state: [prompt_length, input_tokens, cpu%, ram%] is measured before the request, identically in training and serving.
  • Fixed-length requests: v4/v5 generate exactly 200 tokens, so latency is comparable.
  • Load change at a token index, not a time, so every policy faces it at the same point of the response.
  • Statistics: bootstrap 95% CIs on means and on paired per-context differences. A difference is called significant only if its CI excludes zero. Regret is measured against the best fixed strategy in hindsight per context.
  • Stall exclusion: a context is excluded if any run is more than 2x the median of the same condition in the same scenario. Comparing within a condition keeps policies that are slow every time (for example static under oversubscription). Raw data is never deleted.
  • Output equivalence is checked on token IDs for every context.
  • Handoff timings are in-process clone() copies, a lower bound on a real inter-device transfer.

13. Engineering, testing and reproducibility

  • Tests: tests/test_pipeline.py (8 tests) and tests/test_adaptive.py (15 tests) run without the model. All 25 collected test cases passed on 12 October 2026 (55.7 s). tests/test_functional_equivalence.py loads the model and checks that every strategy reproduces model.generate() token for token.
  • evaluate_adaptive.py supports --resume (skip finished contexts and restore bandit state), --report-only (re-analyse saved CSVs), configurable scenarios (--heavy, --switch-token, --ramp), bandit bins (--bandit-edges, --bin-margin) and, in this commit, --keep-awake, which stops Windows from sleeping during long runs through SetThreadExecutionState.
  • run_overnight.cmd resumes the v5 run unattended with HF_HUB_OFFLINE=1 and appends to a log.
  • Every data version is written under its own tag (v2, pilot, v3, v4, v5). Nothing older is overwritten.
  • Environment quirks: Hugging Face downloads needed a TLS workaround (truststore); scripts run with HF_HUB_OFFLINE=1. The fp32 model needs about 4.4 GB. With 16 GB RAM and RAM usage at 92-97% during runs, paging stalls are the main source of outliers.

14. Limitations and open problems

  1. Small samples: 6-8 contexts per scenario in v5, 3 in the v3 adaptive run. Several CIs are wide (ramp bandit vs balanced: -2.3 to 37.8 s).
  2. One machine, one model, CPU only. The thread-budget regimes are specific to this 10-core / 16-thread laptop and will move on other hardware.
  3. Memory pressure: RAM at about 95% causes paging stalls, which required excluding 2 (v4) and 4 (v5) contexts and removing one corrupted v5 context by hand.
  4. Synthetic load: busy-loop worker processes are a simple model of contention. Real co-located workloads also compete for memory bandwidth and cache.
  5. Reaction delay: with a 10-token interval and patience 2, policies switch too late when load arrives suddenly, which cost about 58% in spike.
  6. Online bandit underperforms in v5 (Section 11.4).
  7. The offline DQN goes stale when machine conditions change (seen between v3 and v4). It was trained on loads up to 8 workers only.
  8. The "partitioning" is within one device. Layer stages run sequentially, so stage splits only change thread budgets, not parallelism. A CPU/GPU split (RTX 3050) has not been tried.
  9. The execution graph in src/graph is descriptive (5 coarse nodes plus partition metadata). The scheduler does not search over graph partitions.

15. Next steps

  1. Fix the bandit: attribute cost only to tokens generated after a switch takes effect, retest the stall rule at high load, cap the influence of the DQN prior in bins outside its training range, and add a safety rule that never explores static above the cliff.
  2. Faster reaction to load spikes: an emergency switch when per-token latency jumps (for example 3x the recent median), without waiting for the next interval or for hysteresis. This targets the spike loss directly.
  3. Retrain the DQN on the v4/v5 logs and the load sweep, so it covers 10-14 workers.
  4. More contexts per scenario (at least 15) once memory pressure is reduced, for example with bfloat16 (halves RAM, outputs change slightly) or by closing other applications.
  5. Extend strategies to a CPU/GPU split on the RTX 3050 (needs a CUDA build of torch), which would make the partitions real device partitions.
